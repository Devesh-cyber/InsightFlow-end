# InsightFlow v2: Architecture

> Understand your data before you change it.

This document records *what* we built and *why*. When a decision changes,
update this file in the same commit.

## 1. System overview

```
Browser (React, later)
   |  1. login (email / Google)  -->  Supabase Auth  -->  access token (JWT)
   |  2. API calls with "Authorization: Bearer <token>"
   v
FastAPI backend (Docker, Render free tier: 512 MB, 1 worker)
   |-- Auth check ........ verifies JWT locally with Supabase's public keys (cached)
   |-- Dataset service ... ownership, versions, cache, quotas, conflict checks
   |-- Polars engine ..... parse, infer types, profile, clean, chart data, export
   |
   |--> Supabase Postgres ... datasets, dataset_versions, analysis_cache (RLS on, no policies)
   |--> Supabase Storage .... private bucket "datasets": original upload + one Parquet per version
```

The browser never talks to Postgres or Storage directly. Only the backend does,
so there is exactly one place where access rules live.

## 2. Decisions and the v1 problem each one fixes

| # | Decision | v1 problem it fixes |
|---|----------|---------------------|
| 1 | Every dataset version is an immutable Parquet file in Storage; Postgres points at the current one | Data lived in an in-memory dict; every Render sleep/restart caused "dataset not found" |
| 2 | Parquet as the working format (CSV/XLSX only for upload and download) | CSV round-trips changed column types after restart; zip codes lost leading zeros |
| 3 | One `load_dataset()` path used by every endpoint | Only 1 of 9 services could restore a dataset |
| 4 | Caches keyed by `(dataset_id, version)`; size-capped in MB; results also stored in `analysis_cache` | Unbounded cache; risk of stale results |
| 5 | CPU work runs in the threadpool (sync endpoints), with a job semaphore (`MAX_CONCURRENT_JOBS`) | `async def` + Pandas blocked the whole server during any heavy request |
| 6 | JWT verified locally (JWKS, cached 10 min) | 2 network calls to Supabase Auth on many requests |
| 7 | Optimistic concurrency: writes send `expected_version`; mismatch gives 409 | Two tabs could both write "version N+1" |
| 8 | Write order: Storage first, then DB in one transaction; orphans cleaned later | Storage and DB could disagree after a failure |
| 9 | Type inference applies only lossless changes; ambiguous ones become suggestions | `?` / `-` silently made numeric columns "categorical" |
| 10 | RLS enabled with no policies on all tables; private bucket; secret key backend-only | Tables were potentially readable via Supabase REST with the public key |
| 11 | One error shape for every error, including crashes, with a request id | Mixed `{detail}` / `{message}` shapes; no way to trace a failure |
| 12 | Exact dependency pins + tests that run offline | Unpinned deps pulled pandas 3.0; the only test file was broken |

## 3. Data model

See `supabase/migrations/0001_init.sql`.

- **datasets**: owner, name, source file info, sheet, `current_version`, counts, status
- **dataset_versions**: `(dataset_id, version)` unique; `parquet_path`; the `operation`
  that produced it (type + params); `summary` (before/after counts, warnings)
- **analysis_cache**: `(dataset_id, version, kind, params_hash)` → JSON result

Storage layout (paths are generated by the server, never from user input):

```
datasets/{user_id}/{dataset_id}/source.{csv|xlsx}
datasets/{user_id}/{dataset_id}/v{n}-{random}.parquet
```

Revert = create a new version row that points at an older Parquet file (no copy).
Retention keeps the last `MAX_VERSIONS_PER_DATASET` versions; a file is deleted
only when no remaining version references it.

## 4. Upload pipeline (Phase 1, built)

Protocol: `POST /v1/datasets?filename=sales.xlsx[&sheet=Q1]` with the raw file as the
body (`Content-Type: application/octet-stream`). No multipart: the body streams straight
to disk while bytes are counted, so an oversized file is rejected the moment it crosses
the limit and is never held in memory. From the browser: `fetch(url, {method: "POST", body: file})`.

1. Stream the request body to a temp file, counting bytes; abort past the limit
   (`MAX_UPLOAD_MB` for CSV, `MAX_XLSX_UPLOAD_MB` for Excel).
2. Detect the real type from bytes: XLSX must be a valid zip (with zip-bomb guard);
   CSV must decode as text. Detect encoding (UTF-8 / Latin-1 → UTF-8) and delimiter.
3. Parse with Polars (XLSX via the `calamine` engine). For XLSX, list all sheets;
   load the first, allow reloading another.
4. Every cell is read as TEXT first (both formats), then typed by one shared engine.
   Reason: letting Polars guess Excel types from the first rows silently turned a later
   "?" into null and dropped the row (reproduced and covered by a regression test).
   Type inference: standard missing markers (`""`, `NA`, `N/A`, `null`, `NaN`) become
   null; clean numeric/date columns get typed; leading-zero IDs stay text; anything
   ambiguous (`?`, `-`, `₹1,200`) is left as-is and reported as a suggestion.
5. Write source file + `v1` Parquet to Storage, insert DB rows, compute overview.

### Measured performance (Python 3.12, Polars 2.0, 2 threads, laptop CPU)

| Step | Input | Time | Server peak RAM |
|------|-------|------|-----------------|
| Upload + type inference | 24 MB CSV, 267k rows | ~1.4 s | ~240 MB |
| Upload | 11 MB XLSX, 200k rows | ~2.1 s | ~235 MB |
| overview / health / columns | 267k rows | 0.2-0.45 s (cached afterwards: ~6 ms) | |
| Preview / apply a cleaning step | 267k rows | ~0.2-0.3 s | |
| Export CSV | 267k rows | ~0.15 s | |
| Export XLSX (streaming) | 110k x 9 = 1M cells | ~6.6 s | flat |
| **Whole flow above, one server** | | | **~310 MB** (idle ~105 MB) |

Two findings from these measurements changed the design:
- Polars' Excel reader drops rows when it guesses types from a sample → read all cells as text.
- Polars' `write_excel` held the entire workbook in memory (**856 MB** for 267k rows) → stream
  with xlsxwriter `constant_memory`, and cap XLSX export at `MAX_XLSX_EXPORT_CELLS` (CSV is uncapped).

Render's free plan is 0.1 CPU, so CPU-heavy steps run several times slower there; memory fits.
Limits: CSV 25 MB, XLSX 10 MB, one heavy job at a time, allocator returns memory immediately
(`_RJEM_MALLOC_CONF` in the Dockerfile).

## 5. Read path and caching (Phase 2)

Every read goes through `AnalysisService` (app/services/analysis.py):

```
resolve(user, dataset, version?)   ownership check; current version unless asked
frame(resolved)                    Parquet from local disk cache, else downloaded once from Storage
cached(resolved, kind, params, fn) memory (LRU, MB-capped) -> Postgres analysis_cache -> compute
```

- Keys always include the version, so cached results can never be stale.
- `overview`, `columns`, `health` are also persisted in Postgres (they survive Render sleeping);
  parameterised results (charts, relationships, column detail) stay in memory only.
- Parquet files are immutable, so the disk cache needs no invalidation; it's trimmed by size.

## 6. Cleaning model (Phase 4)

- Each operation = strict Pydantic params (`extra="forbid"`) + a pure function `df -> df`.
- `run_operation` adds a hidden row id, applies the operation, then measures the effect:
  rows removed, cells changed per column (type-aware: `"25" -> 25` is not a change, `"?" -> null` is),
  dtype changes, and up to 20 before/after sample rows. **Preview and apply share this code**,
  so what you preview is exactly what's applied.
- Apply = new Parquet file → Storage → `add_version(expected_version)` (row lock + check) → 409 on conflict.
- Revert = new version pointing at the old file (zero copy). Pruning deletes a file only when no
  remaining version references it.
- Health issues carry ready-to-run operations with a recommended option and the reason, e.g.
  median when |skew| > 1, "Unknown" rather than mode for high-missing text, nothing when ≥70% missing.
- The pandas recipe walks the version lineage (following reverts) and is executed in a test to
  prove it reproduces the result.

## 8. Security checklist

- [x] JWT: allow-listed algorithms only, audience + issuer + expiry checked, `role=authenticated` required
- [x] Auth provider outage returns 503, not 401 (users aren't logged out by an outage)
- [x] CORS: explicit origin list, no cookies, no wildcard in production
- [x] Crashes never leak internals; full trace goes to logs with the request id
- [x] RLS on, no policies, grants revoked; private bucket
- [x] Container runs as non-root
- [x] Size limit enforced while streaming; per-format limits
- [x] XLSX: real zip + workbook check, zip-bomb guard (size, ratio, entry count); .xls / encrypted files rejected with a clear message
- [x] CSV: NUL-byte check, encoding detection, everything normalised to UTF-8
- [x] Server-generated storage paths; files never overwritten (random suffix)
- [x] Per-user quota (race-safe via advisory lock) and upload rate limit
- [x] Secret key sent only in the `apikey` header and never logged
- [x] XLSX export never writes formulas (text like `=HYPERLINK(...)` stays text)
- [x] Cleaning params validated strictly; unknown fields rejected; find/replace is literal (no regex)
- [x] Dependency audit: `pip-audit -r requirements.txt` → no known vulnerabilities (at build time)
- [x] Memory measured across the full flow: ~310 MB peak of 512 MB
